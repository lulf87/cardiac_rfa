# METHODS_PARAMETER_AUDIT

## Scope

- Current implementation audited: `simulation/stage17_controlled_rebuild/`
- Current canonical controller config selected by the stage17 run scripts: `simulation/stage17_controlled_rebuild/configs/controller_selected_stage17.yaml`
- Current canonical latency config selected by the stage17 run scripts: `simulation/stage17_controlled_rebuild/configs/latency_enabled.yaml`
- Manuscript audited for wording and explicitness: `papers/V13/CMBBE_RF_ablation_reduced_model_main.docx`
- Legacy code was not deleted or rewritten during this audit. In particular, `simulation/stage16_uq_metrics_ready/` and older `stage*` folders remain archival or frozen baselines rather than the current deterministic implementation.
- Legacy controller variants still exist in `simulation/stage17_controlled_rebuild/configs/`, but the current stage17 run scripts point to `controller_selected_stage17.yaml`, not to `controller_generic_temp_limited_enabled.yaml` or the trial controller files.

## Audit vocabulary

- `FOUND`: located in the current implementation with a traceable code path.
- `AMBIGUOUS`: partially located, but the implementation or manuscript wording leaves the item under-specified, indirect, or not uniquely named.
- `NOT FOUND`: not located in the current implementation or not recoverable from the current manuscript/code path.
- Manuscript explicitness:
  - `YES`: stated explicitly in the current manuscript text.
  - `NO`: not stated explicitly in the current manuscript text.
  - `AMBIGUOUS`: likely present only inside Word equations or partial prose, but not recoverable cleanly from the current DOCX text extraction.

## High-level findings

- The current stage17 implementation is sufficiently concrete to recover the active reduced source construction, contact-dependent power scaling, source shift, cooling surrogate, controller logic, sensor definition, power limits, latency loop, Arrhenius accumulation, and lesion metric extraction.
- The base reduced source is implemented algorithmically, not as a standalone analytic `q_reg(x,y)` formula. A reproducible equivalent exists in code, but an analytic closed form does not.
- The current controller is not a black box in code: it is a piecewise linear ramp-down controller with explicit `target`, `ceiling`, `min_power`, `max_power`, `sample_period`, and `ramp_down_gain`. The manuscript does not currently state several of those details.
- The current model is planar Cartesian 2D. No axisymmetric terms were found in the current solver.
- Solver tolerances and pinned package versions were not found. The current implementation uses direct sparse linear algebra and an unpinned `requirements.txt`, so version-level reproducibility is incomplete.

## Methods-critical manuscript/implementation gaps

- The manuscript says the controller uses a "surface-adjacent temperature surrogate", but the current code implements this specifically as `T[1, :].max()`, i.e. the maximum temperature along the first interior depth row across the full lateral domain.
- The manuscript gives `70 °C`, `80 °C`, `0.05 s`, and sample-and-hold wording, but it does not explicitly state the current controller ramp-down formula, `min_power_W = 15.0`, `max_power_W = 90.0`, or `ramp_down_gain_W_per_C = 6.0`.
- The manuscript states that contact affects source strength and cooling, but the exact current code values for some coefficients are not recoverable cleanly from prose-only DOCX extraction. This is especially true for equation-level symbols such as the source-gain and cooling-reduction coefficients.
- The manuscript states a reduced 2D framework, but the current code is more specific: a planar Cartesian cross-sectional solver with a per-depth source scaling. That exact dimensional interpretation is not stated explicitly enough in the manuscript.
- `simulation/stage17_controlled_rebuild/configs/latency_enabled.yaml` contains `record_dt_s`, but the current solver path uses only `post_pulse_duration_s`; no current code path consumes `record_dt_s`.
- Legacy controller configs remain present in the repository, so audit work should continue to distinguish "current implementation" from "legacy or trial config" rather than assuming every controller YAML is active.
